Inside partmgr

Everything a programmer needs to understand, build, test and extend partmgr: the partition table code, the rules it writes by, the backup format, the UEFI program around it and the way it is tested.

Overview

What partmgr is from the inside, the principles that shaped it, and a map of this manual.

What this manual covers

The user manual explains what partmgr does. This manual explains how: after reading it you should be able to find your way in every source file, build and test partmgr, and change the way it reads or writes tables without breaking a disk. It assumes the NESH developer manual for what the two programs share: the build pipeline, elf2efi.py, the freestanding runtime and the platform layer.

Design principles

  • The table code knows no firmware. Reading, changing and writing tables (ptable.c, ptedit.c, ptwrite.c) reach the disk only through a read and a write function (PtDev). The same code runs on a UEFI block device and, in the tests, on a disk image file, where sfdisk and parted check every table it writes.
  • Nothing is written until Write. Every change is made on a PtTable in memory; only pt_write and pt_restore write to a disk (decision D21).
  • Protection at the lowest level. The disk partmgr was started from, and a write-protected one, get no write function at all: no mistake in the interface can write them.
  • Only the table. partmgr never writes inside a partition. The blocks it writes are the MBR, the extended boot records and the GPT headers and arrays.
  • Damage is shown, not hidden. A damaged table is read as far as possible and explained with notes; writing a table always writes a clean and complete one.
  • One project with NESH. Same repository, same release, same platform layer, same disk names; no EDK2 code (D7).

How partmgr.efi is linked

The Makefile lists two groups: PARTMGR_SRC, the portable part also compiled into the Linux test tool, and PARTMGR_EFI_SRC, which adds the program and what it needs from NESH's runtime and platform layer:

PARTMGR_SRC := src/partmgr/ptable.c src/partmgr/ptedit.c src/partmgr/ptwrite.c src/partmgr/units.c \
	src/lib/crc32.c src/lib/util.c
PARTMGR_EFI_SRC := $(PARTMGR_SRC) src/partmgr/main.c src/partmgr/diskview.c src/partmgr/ui.c src/partmgr/disks_efi.c \
	src/lib/libc.c src/lib/fmt.c src/pal/pal_efi.c src/pal/pal_common.c

The objects are compiled with the EFI flags of NESH, linked with tools/efi.lds into build/partmgr.so and converted to PE32+ by tools/elf2efi.py. pal_efi.c is the same file NESH uses: it does not know which program it starts. It calls app_main and names the program app_name in fatal errors; src/partmgr/main.c defines both, as src/core/shell.c does for NESH. So partmgr gets the 1 MiB private stack, the console, the keyboard and the file functions of NESH, and the shell itself is not linked in.

Architecture

Layers

Start-up

efi_main (in pal_efi.c) sets up the firmware globals, the volumes and the arguments, switches to the private stack and calls app_main. partmgr hides the cursor and loops on the list of disks: every turn calls pm_disks, which locates the block devices again (so R, or any key, rescans), and reads each disk's table to fill the columns. Enter calls pm_disk_screen; Q resets the colours, clears the screen and returns 0 to the caller.

Life of a change

The data model

Three structures carry everything: the disk, the table and its partitions.

PtDev: the disk

typedef struct {
    PtReadFn read;
    PtWriteFn write;   /* NULL: the disk is read-only */
    PtRandomFn random;
    void *ctx;
    uint32_t bsize;   /* bytes per block: 512 or 4096 */
    uint64_t nblocks; /* size of the disk in blocks */
} PtDev;

read and write move whole blocks and return 0 or a PAL_E* code; random fills identifiers. On UEFI ctx is the EFI_BLOCK_IO_PROTOCOL; in pttool it is the image file. write is NULL for the boot disk and write-protected media, and every write function of ptwrite.c then returns PAL_EROFS.

PtTable and PtPart

FieldMeaning
kindPT_NONE, PT_MBR or PT_GPT.
mbr_sig, disk_guidThe disk identifier of each kind.
first_usable, last_usableGPT: the blocks partitions may use.
max_entries, entry_sizeGPT: the entry array (usually 128 × 128 bytes).
primary_entries_lba, backup_lba, backup_entries_lbaGPT: where the copies are (for backups).
primary_ok, backup_ok, hybridGPT: which copies passed the checks; block 0 has more than the protective entry.

parts, npartsThe partitions, in table order (MBR: primary and extended, then logical in disk order).

changedSomething changed since the table was read (drives the title and Esc).

A PtPart has num (the GPT entry index + 1, or 1–4 and 5… on MBR), role (PT_PRIMARY, PT_EXTENDED, PT_LOGICAL), start and size in blocks, the MBR fields mbr_type, active, ebr_lba (the block of the record that describes a logical partition), the GPT fields type_guid, guid, attrs, name (UTF-8), and changed, which puts the star on the screen. pt_free releases the array; a table is otherwise a plain value.

PtFree

pt_free_space returns the free areas as PtFree: start, size and logical, true for an area inside the extended partition, where only a logical partition fits. Areas are aligned and at least 1 MiB; the screen merges them with the partitions and sorts by start.

Reading tables: ptable.c

What block 0 says

pt_read reads block 0 and decides:

  1. 55 AA at bytes 510–511 and every entry's status byte 00 or 80: a valid MBR sector.
  2. An entry of type EE: a protective MBR, so the disk is GPT; other entries next to it make it hybrid.
  3. A valid MBR sector that is not the boot sector of a file system (a jump instruction and NTFS, EXFAT or FAT at their places): an MBR.
  4. Otherwise: if block 1 starts with EFI PART, a GPT whose protective MBR was wiped; if block 0 is a file system's boot sector, a disk formatted without a table; else nothing.

GPT: two copies, checked

gpt_copy reads a header and its entry array and accepts them only if every check passes: signature EFI PART; header size between 92 bytes and one block; header CRC-32 (computed with the CRC field zeroed); MyLBA equal to where it was read; a possible layout (first ≤ last usable < disk size, entry size ≥ 128 and a multiple of 8, at most 1 MiB of array); the array readable and its CRC-32 right. The primary copy is read from block 1, the backup from the primary's AlternateLBA — or from the last block when the primary is damaged. The primary is used when good, else the backup; each failure is a note saying which check failed. Entries whose type GUID is zero are empty and skipped; names are converted from UTF-16.

MBR: the chain of logical partitions

The four entries of block 0 give the primary partitions and at most one extended partition (types 05, 0F, 85). mbr_logicals then follows the chain: each record, at a block inside the extended partition, has in entry 1 its logical partition relative to the record and in entry 2 the next record relative to the start of the extended partition. The walk stops with a note on a record without 55 AA, on a link that does not move forward or leaves the extended partition, and after 128 records — so a looping or broken chain cannot hang partmgr. Logical partitions are numbered from 5 in chain order, as Linux does.

Type names

Two tables at the end of ptable.c, gpt_types and mbr_types, give the names. Their order is the order of the list the user chooses from (pt_type_at); the last four MBR entries (extended and protective) are names only and never offered.

Changing tables: ptedit.c

A table from zero

pt_new replaces the table with an empty one: all fields cleared, lba0 zero (no boot code), new identifiers from dev->random. A GPT gets 128 entries of 128 bytes: the array takes 32 blocks of 512 bytes (4 of 4096), so first_usable is 34 (or 6) and last_usable is the block before the backup array. GUIDs are random with the version 4 and RFC 4122 variant bits set; an MBR signature is random and never zero. PT_NONE is the empty table that pt_write turns into deleting the table.

Free space

Free areas are the gaps between spans. At the top level the spans are the partitions that are not logical, inside the GPT usable area or blocks 1 … min(disk, 232) − 1 of an MBR. Inside the extended partition the spans are:

  • its first block, always reserved: the chain must start there;
  • for each logical partition, the block before it and the partition: every logical partition needs a record somewhere before it, and the block right before it is the one that is always free.

A gap becomes a PtFree after rounding its start up to 1 MiB (for logical gaps, from the block after the gap's first one, which will hold the new record) if at least 1 MiB is left. This rule is what lets the space of a deleted first logical partition be used again: the record of the next one moves to the first block of the extended partition when writing, and the space in front of it is free.

Adding

pt_add checks the request and returns a message for the user, or NULL:

TableRules
GPTType not zero; inside the usable area; no overlap; a free entry (the lowest); name ≤ 36 UTF-16 units. The new partition gets a random GUID.
MBR primaryType not zero and not extended; not in block 0; below 232 blocks; no overlap with top-level partitions; a free slot among 1–4.
MBR logical, no extended yetA free slot for the extended partition, which is created over the whole raw gap containing the start, from the gap's start rounded to 1 MiB; type 0F if it reaches beyond block 0xFFFFFF (8 GiB, the reach of CHS), else 05. The logical partition must start after the extended one's first block; its record is that first block.
MBR logical in the extendedInside the extended partition and inside a logical gap, starting after the gap's first block, which becomes its record (ebr_lba).

After an MBR change renumber sorts the partitions (primary and extended by number, logical by start) and numbers the logical ones 5, 6…; a partition whose number changes is marked changed.

Delete, type, name, active

  • pt_delete removes a partition; the extended one takes its logical partitions with it.
  • pt_set_type refuses a zero type, and on MBR any change between extended and non-extended types.
  • pt_set_name is GPT only, 36 UTF-16 units.
  • pt_set_active is MBR only, not for the extended partition, and clears the flag everywhere else.

Writing: ptwrite.c

GPT

write_gpt recomputes the last usable block from the real disk size (so an enlarged disk gets its backup at the end) and refuses a table whose partitions do not fit. It builds the entry array (entries at index num − 1, names converted to UTF-16) and writes, in this order:

  1. block 0, the protective MBR — unless the table is hybrid, whose block 0 is left alone: the first 440 bytes as read (boot code; zero for a new table), one entry of type EE from block 1 over the disk (at most 232 − 1 blocks), CHS 00 02 00 as the specification gives, 55 AA;
  2. the primary array at block 2, then the primary header at block 1;
  3. the backup array just before the last block, then the backup header in the last block.

Headers are revision 1.0, 92 bytes, with the array CRC and then the header CRC. Both copies are always written, which is also how a damaged copy is repaired.

MBR

write_mbr writes block 0 with the boot code as read, the signature, one entry per primary or extended partition at slot num − 1, and 55 AA. Before it, a GPT header in block 1 or in the last block is cleared — if it is not inside a partition of the new table — so that no system finds the old GPT. Every entry gets CHS fields computed with 255 heads and 63 sectors, or FE FF FF beyond cylinder 1023.

Then the chain, with the logical partitions in disk order. Record i goes:

  • for the first logical partition, to the first block of the extended partition;
  • for the others, where it was (ebr_lba) if that block is still between the previous partition and this one, else to the block just before the partition — which ptedit.c keeps free.

Entry 1 of a record is its logical partition relative to the record. Entry 2 links to the next record: type 05, start relative to the extended partition, and size from the next record to the end of the next logical partition — the convention of fdisk and sfdisk, which the tests check byte by byte. An extended partition without logical ones gets an empty record with 55 AA.

No table

For PT_NONE, erase writes zeros to block 0, block 1 and the last block: the MBR and both GPT headers, which is what every system looks at. Nothing else is touched.

Backup and restore

The backup file

pt_backup builds the file in memory from the table as read from the disk. All numbers are little-endian.

OffsetSizeContent
08PARTMGR1
84Format version: 1
124Block size of the disk
168Size of the disk in blocks
244Number of extents
28…For each extent: first block (8), number of blocks (4), the blocks
end − 44CRC-32 of everything before it

The extents are block 0 and, for a GPT, block 1, the primary array, the backup header and the backup array; for an MBR, the first block of the extended partition and every logical partition's record. A disk without a table has nothing to back up.

Restore

pt_restore checks the whole file before writing a block: the magic, the CRC, the version, the block size and the disk size (a backup never goes to a different disk), and every extent inside the disk and inside the file, with no data left over. It reads the current table, writes the extents, and — when the backup has no GPT but the disk had one — clears the old GPT's headers and arrays except where a restored partition lies, so that restoring over a changed disk gives back the same blocks (the tests compare the images byte for byte).

The UEFI program

Finding the disks: disks_efi.c

pm_disks locates every handle with EFI_BLOCK_IO_PROTOCOL, sorts them by device path text and names them blkN by position — exactly NESH's map — then keeps the whole disks with a medium and a block size of at least 512. The disk partmgr was loaded from is the one whose device path the path of gLoadedImage->DeviceHandle (the partition) starts with, followed by /; it and write-protected media get write = NULL. The kind (NVMe, SATA, USB…) comes from the node names in the device path.

Block I/O goes through a page-aligned bounce buffer from AllocatePages, which satisfies any IoAlign; every write is followed by FlushBlocks. Random bytes come from EFI_RNG_PROTOCOL when the firmware has it, else from a SplitMix64 generator stirred with the time-stamp counter and the clock.

Drawing and dialogs: ui.c

ui_text writes a UTF-8 text at a position, padded or cut to a width counted in characters; it never writes the last cell of the screen, which scrolls some consoles. Dialogs are boxes in the middle of the screen, drawn over it: the caller redraws the screen before the next dialog (draw in diskview.c). ui_input shows a field whose proposed text is replaced by the first character typed; ui_menu is a scrolling list; ui_yesno takes Y, N, Esc. With warn set they are white on red: every operation that destroys data uses them.

The screen of a disk: diskview.c

A View holds the disk, its PtTable, the rows (partitions and free areas merged by start), the selection and the message line. Every action follows the same pattern: may_change refuses on the boot disk and read-only media; dialogs collect the input; one pt_* call changes the table and returns a message on refusal; build_rows and say update the screen. Only three functions reach the disk: write_table (Write), restore and backup (which only reads it); the first two go through confirm_destroy, the red warning that wants the disk name typed. After writing, the table is read back from the disk, so the screen shows what the disk holds.

Sizes: units.c

pm_parse_size reads a number with up to six decimals (point or comma) and a binary unit (B, K, M, G, T, optionally followed by B or iB; s for blocks; no unit means MiB), or rest/all/max, and refuses overflows. pm_fmt_size prints one decimal (194.9 MiB); pm_fmt_exact prints whole MiB or GiB when exact, so that a proposed start reads back to the same block.

Testing

The table code is tested on Linux against sfdisk and parted; the program is tested in QEMU.

pttool

tests/partmgr/pttool.c is the table code compiled for Linux (with AddressSanitizer and UBSan) around an image file. It reads the table, runs commands on it in order, and prints the result as key=value lines:

$ build/tests/pttool disk.img new gpt add primary 2048 204800 C12A7328-F81F-11D2-BA4B-00A0C93EC93B "EFI" write
$ build/tests/pttool disk.img del 2 free
$ build/tests/pttool disk.img backup table.bin
$ build/tests/pttool disk.img -b 4096 size 1.5G

Commands: new gpt|mbr|none, add primary|logical START SIZE TYPE NAME, del, type, name, active, free, write, reread, backup, restore, size. An error prints error=MESSAGE and exits with 1.

The table tests

tests/partmgr/run-tests.py, run by make test:

  • Reading. Images built with sfdisk — GPT with 512- and 4096-byte blocks, gaps, entries out of order, accented names, attributes; MBR with primary, extended and logical partitions; empty tables — must read exactly as sfdisk --json reports them. Then 13 kinds of damage (broken primary header or array, broken backup, both broken, wiped protective MBR, hybrid MBR, enlarged disk, looping chain, record without signature, partition beyond the end, whole-disk FAT, invalid entries) must be read as well as possible and noted.
  • Sizes. What pm_parse_size accepts, refuses and prints.
  • Writing. Every table partmgr writes is read back by sfdisk (which must find what was asked and nothing wrong with --verify) and by parted: new tables, logical partitions creating the extended one, changes to tables made by sfdisk (identifiers of untouched partitions unchanged), deleting and refilling the first logical partition, deleting the extended one, GPT to MBR and back, deleting a table, repairing, an enlarged disk, boot code kept or cleared, a hybrid MBR left alone, and the refusals.
  • Independently of partmgr, a Python function reads every MBR written byte by byte (CHS fields, the chain, the link sizes) — and agrees with the MBRs sfdisk writes.
  • Backups are restored over a changed disk, which must equal the original byte for byte; backups of another disk, damaged ones, and disks without a table are refused.

The tests were checked by breaking the code on purpose — logical numbering, sizes off by one, the boot flag, the backup GPT's CRC, the link sizes of the chain, the CHS heads: each break fails them. Where sfdisk lacks --sector-size (util-linux 2.39, the version of Ubuntu 24.04 and of CI) the 4096-byte comparisons are skipped and the script says SKIPPED.

In QEMU

make qemu-partmgr runs tests/partmgr/qemu-test.py. It boots NESH in QEMU/OVMF from a virtual FAT disk holding partmgr.efi, attaches test disks made by sfdisk, starts partmgr from the prompt and drives it with sendkey through the QEMU monitor. Everything partmgr draws also reaches the serial console; the test strips the terminal sequences, makes every run of blanks one space (so dialog texts wrapped over two lines still match), and waits for the expected text after the previous match — the screen is drawn top to bottom, so rows come before the message line under them.

  1. Looking: the list (names as in NESH's map, the boot disk marked), every row of both disks, the return to NESH, and the disks identical byte for byte.
  2. Changing: the boot disk refuses; on the GPT disk a new partition (start, size, type, name), a rename, a delete, Esc asking, a wrong disk name refused, Write; on the MBR disk a logical partition (renumbering the next one), the active flag, a backup to a writable FAT disk, Write, delete the table, restore. Then, outside QEMU, sfdisk must find the GPT disk exactly as asked and the MBR disk exactly as before.

Extending partmgr

Adding a partition type

Add the GUID and name to gpt_types, or the byte and name to mbr_types before the last four entries, in src/partmgr/ptable.c. The order is the order of the list on the screen. Add the type to the tables of the user manual, and a check in run-tests.py if its name matters.

Adding an action to the screen of a disk

  1. Put the change of the table in ptedit.c, as a function that returns NULL or a message and sets changed; test it through a new pttool command.
  2. In diskview.c, write the action: may_change, the dialogs (redraw with draw before each), the call, build_rows, say. Add its key to the loop of pm_disk_screen and to the key bar in draw.
  3. Anything that writes a disk must go through confirm_destroy.
  4. Extend qemu-test.py, and describe the key in the user manual.

Adding a note

Call note(t, ...) in ptable.c where the problem is found, add the damaged case to run-tests.py with has_note, and explain it in the table of notes of the user manual.

Conventions

  • The code style, English texts and help rules of NESH apply (see the NESH developer manual).
  • Delete a partition: remove it from the table. Wipe: destroy its contents. The code, the texts and the manuals never use one for the other.
  • Blocks are written only in ptwrite.c, and only by pt_write and pt_restore.
  • Messages for the user are sentences without a capital or a full stop at the end when they come from the table code (pt_add and friends); the screen puts them in dialogs as they are.
  • Line counts in this manual are generated: run make docs after changing a file.

Glossary

Block I/O
The UEFI protocol that reads and writes the blocks of a disk or partition.
CHS
Cylinder/head/sector addresses of old BIOSes, still stored in MBR entries next to the block numbers.
EBR
Extended boot record: the one-block table in front of each logical partition, chained to the next.
Extent
A run of blocks saved in a backup file, with its position.
Hybrid MBR
A GPT disk whose block 0 also lists some partitions for BIOS systems; partmgr reads it as GPT and leaves block 0 alone.
Note
A sentence the reader adds to a table about something unusual it found.
Protective MBR
Block 0 of a GPT disk: one entry of type EE over the disk.
Span
In ptedit.c, a run of blocks in use; free areas are the gaps between spans.
